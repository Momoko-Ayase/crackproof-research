## GitBook Documentation Editing

This repository contains documentation synced with GitBook via Git Sync.

Before editing GitBook-synced Markdown, YAML, or asset files, make sure the GitBook skill is available and up to date in your local agent environment. Prefer installing or updating it with:

```bash
npx skills add gitbookio/gitbook-skills
```

This command may add or update local agent skill files. Use them only as local agent instructions; do not commit those installed skill files or any tool-generated agent configuration unless the user explicitly asks for it.

If `npx` is unavailable, load the skill from:

https://gitbook.com/docs/skill.md

When making changes, preserve GitBook sync metadata such as frontmatter, `SUMMARY.md`, `gitbook-docs.yaml`, `.gitbook/`, and asset links unless the requested edit explicitly requires changing them.

## Documentation requirements

These rules apply to all content in this repository: the Home pages in `home/`, the Windows pages in `internals/windows/`, the Android native-library pages in `internals/android-so/`, the Verification & reference section in `reference/`, the Senbei section in `senbei/`, and the Arare section in `arare/`. Each published section has five language variants: English (`en`), Simplified Chinese (`zh-cn`), Traditional Chinese (`zh-tw`), Japanese (`ja`), and Korean (`ko`).

- **Research document, not product documentation.** Write about how the protection works internally — never how to use any tool. Do not name CrackProof unpacking/dumping tool implementations (neither the project's own tooling nor third-party ones). Generic analysis tools (IDA, Ghidra, debuggers, memory-forensics frameworks) may be named only where a technique directly involves them. Never add meta-commentary about these rules to the docs themselves — no "this document is/is not..." sections; the rules govern the writing, they are not content. **Exception:** the `senbei/` and `arare/` sections are product documentation of the project's own tools; there the tool is the subject, so it is named and its usage is documented. The Home pages may carry a navigation card and a one-sentence pointer to those sections; the research sections (`internals/`, `reference/`) still never reference them.
- **Product naming.** Use CrackProof® on first mention on each Home page and in legal notices; use plain "CrackProof" elsewhere. The Windows product is CrackProof for Windows® (capital P; the developer is HyperTech, capital T). CrackProof is a multi-platform family. This repository covers Windows PE files and Android native libraries; do not imply that either section describes the whole product family.
- **Component names.** Use CrackProof-internal names only (KONN, HtpecIt, HtdpStub2, Htsysm, Htsysm7679, status codes, `.kmiat`). Never name machine- or title-specific driver files; describe them by driver generation or a generic artifact label. Those filenames are per-deployment artifacts, not part of the scheme. Never name protected products, publishers, or hardware platforms; use generic build families.
- **Language parity.** Author all five languages (`en`, `zh-cn`, `zh-tw`, `ja`, `ko`) directly in natural native developer usage for each language and region (`zh-cn` uses Mainland developer terminology; `zh-tw` uses idiomatic Taiwan developer terminology rather than automated OpenCC conversion from `zh-cn`; `scripts/s2tw.py` has been retired). Keep the published GitBook page paths, source directories, overview filenames, frontmatter `icon:` values, GitBook block structures, and `SUMMARY.md` hierarchy identical across all five languages (Windows: `file-structure/`, `loading-and-pe-repair/`, named overviews such as `file-format.md` / `data-transforms.md`). GitBook may still normalize a synced path after a group slug is renamed; do not let that drift back into the repo. Non-Mermaid code blocks stay byte-identical across all five languages; `mermaid` blocks translate only quoted display labels. Never place `_emphasis_` directly adjacent to CJK, Japanese, or Korean characters (use `*...*` or `**...**`).
- **Style.** Readability takes priority. Use established technical terms when they exist, keeping standard English identifiers and community-standard English loanwords (such as `fixture`, `hook`, `RVA`, `VA`, `OEP`, `IAT`, `IDT`, `TLS`, `CLR`, `ASLR`, `PLT`, `GOT`) rather than forced literal translations. When no stable term exists, describe the observed structure or behavior literally. Do not invent names, labels, pseudo-technical compounds, awkward metaphors, or anthropomorphism, and avoid defensive disclaimers refuting hypothetical misunderstandings. Perform a separate native-developer pragmatics review pass after editing in every language. Prefer short sentences, concrete subjects, and one main idea per paragraph. Quote every YAML frontmatter `description:` value on a single line and keep descriptions short (`en` ≤ ~130 chars; `zh-cn`, `zh-tw`, `ja`, and `ko` ≤ ~56 chars).
- **Correctness.** Test every code snippet before publishing. From the repository root, run `python verification/run_tests.py` for the reference implementations and `python verification/verify_docs.py` for the Python blocks across all five Windows documentation languages (`en`, `zh-cn`, `zh-tw`, `ja`, `ko`). Both must pass. The Markdown checker requires every Windows page containing Python blocks to appear in its explicit coverage list. When a snippet changes, update the published `reference/` pages and preserve identical code blocks across all five languages. Other snippet languages require their applicable build or execution checks; the Python checks don't establish runtime behavior or commercial parity.

The reference pages use GitBook-side file names (`detect.py.md`, `sample-debug-logs.md`, …); each language's `SUMMARY.md` is the page list. - **Navigation parity.** Keep the `en`, `zh-cn`, `zh-tw`, `ja`, and `ko` `SUMMARY.md` trees structurally identical.
