# Huffman 與 LZ 壓縮

壓縮塊使用緊湊 Huffman 表，後接 LZ 風格流。表是 3 字節項組成的森林：一個 u16 符號/子結點字段和一個 u8 碼長字段。8 個輸入位選擇根。最高位（`0x8000`）標記葉子；內部結點存放兄弟對中第一個的下標，再用一個輸入位在兩者之間選擇。

這與 [Windows Huffman/LZ 格式](https://app.gitbook.com/s/sFi4W2Zr1UBoxZd5YI3A/data-transforms/compression)是同一套 token 語言。16 位前綴查找可以加速碼的前若干位；更長的碼再沿樹走。

**token 格式。** 第 8–9 位選擇模式，第 0–7 位是載荷：

| 模式 | 含義 |
| --- | --- |
| `0x000` | 字面量：寫出載荷字節 |
| `0x100` | 計數累加器：把載荷接到大端 pending 值上（本身不輸出） |
| `0x200` | 遊程填充：把剛寫出的 1/2/4 字節單元重複 `pending × payload` 次 |
| `0x300` | LZ 回指：從輸出遊標後方 `pending + payload` 字節處拷 `payload` 字節 |

只有距離非零、不指向輸出起點之前、且請求長度不超過聲明目標時，回指才合法。單元寬度不是 1、2 或 4 屬於格式錯誤：解碼器不得把這些字節計為已寫出。一份實驗筆記記錄過對異常寬度的 skip-run 子情形；該行為未在跨構建解碼器中復現，不屬於已接受的格式。

只有當位讀取器耗盡允許的輸入、且輸出恰好達到聲明大小時，該塊才有效。過早的結束標記、懸空樹下標、零寬度葉子，或文檔填充之外的尾字節，都是格式錯誤，而不是部分成功。
