# 格納レイアウト

保護された Android 版 IL2CPP ビルドでは、メタデータは次のいずれかの形態で格納されます。

| 形態 | 格納場所 | 展開後のフォーマット |
| --- | --- | --- |
| 外部 `global-metadata.dat` | `assets/bin/Data/Managed/Metadata/` 配下（または Split Asset APK 内）の独立ファイル | バージョン `24`（`v24.1`）・`29`・`31`・`39` の標準 `0xFAB11BAF` ヘッダー |
| 埋め込みスリム + XOR ブロブ | 復元後の `libil2cpp.so` イメージ内にある `0x2701F30` バイトのデータブロブ | マスク解除後の先頭 dword `[0x9732CA38, 0xBAC4374F]` を `[0xFAB11BAF, 24]` へ書き換えた形式 |

{% hint style="info" %}
Stage 2 の `0x5C` レコード記述子に含まれる `metadata_offset` / `metadata_size` フィールドが保持しているのは、プロテクターモジュールのロード・再配置・インポート用メタデータであり、IL2CPP の `global-metadata.dat` ではありません。外部 `v24.1` の `global-metadata.dat` をモジュール `0x0C` と対応付ける際は、両方のファイルが同一のアプリケーションパッケージに属している必要があります（Split APK 間で `AndroidManifest.xml` の `package` と `versionCode` / `versionCodeMajor` が一致していること、または同一の `<root>/lib/<abi>/` と `<root>/assets/` ツリー下にあること）。
{% endhint %}

## 埋め込みスリム + XOR 方式

バージョン `24` の初期ビルドの一部では、`assets/` に `global-metadata.dat` を置かず、復元後の `.so` データセクション内に `0x2701F30` バイトの XOR マスク済みブロブを埋め込みます。

* **構造:** `0x100` バイトのヘッダー（リトルエンディアン `u32` が 64 ワード、ヘッダーの各ワードに個別の 32 ビット XOR キー）に続き、不規則な長さのボディセグメントが 256 個並びます（セグメントごとに 1 つの 32 ビット XOR キーが内部の dword 列へ適用されます）。
* **ヘッダープローブと修正:** 先頭 2 つの dword を `[0x39184C70, 0xD901AFD4]` と XOR すると、バイトスワップされたセンチネルペア `[0x9732CA38, 0xBAC4374F]` が現れます。64 個のヘッダーキーと 256 個のセグメントキーからなる埋め込みキーストリームを適用したあと、先頭 2 つの dword を `[0xFAB11BAF, 24]` へ書き換えることで、有効なスリム版バージョン 24 メタデータファイルが得られます。
* **鍵導出の解析状況:** 実行時にはメタデータローダーがこれら 320 個の `u32` キーを動的に生成しますが、`.so` バイナリ単体からキーストリームを静的に導出する経路は未解明です。同一系統の後発ビルドでは、シード付き `MethodDef` 置換を用いた外部 `global-metadata.dat` 方式へ移行しています。
