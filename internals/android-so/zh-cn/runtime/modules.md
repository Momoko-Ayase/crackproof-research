# 运行时模块

下列命令标识来自第二阶段记录。职责取自这些模块落地之后运行的函数。ELF 恢复所需的标识仍在[模块记录流](../restoration/module-streams.md)。环境与完整性行为汇总在[环境与完整性检查](environment-checks.md)。

标成「仅观察到」的标识作为记录出现过，其含义尚不清楚。

## 解释器与移交

| 标识 | 职责 |
| --- | --- |
| `0xE2`–`0xE8` | 嵌套记录流解释器。`0xE2` 就是第二阶段自身 |
| `0xF3`–`0xF8` | 交给下一层解释器的直接数据对象 |
| `0xD0` | 第一阶段移交的文件尾映射 |
| `0x98` | 最终移交：复制恢复后的映像并调用 `.init_array`。对应 Windows 状态 `280` |

## 恢复

| 标识 | 职责 |
| --- | --- |
| `0x9B` | 恢复工作流：页权限，消费 `0x9D` 和 `0x9E` |
| `0x9D` | 受保护容器：描述符、分段、压缩块流 |
| `0x9E` | 隐藏的动态符号补丁（`dynsym` / `dynstr`） |
| `0xB9` | 与元数据相关的数据。在 IL2CPP 库上是真实载荷；在部分原生库上为空或无数据 |
| `0x0C` | 仅 IL2CPP。把 `mmap` 换成挂钩，在映射 `global-metadata.dat` 时恢复方法令牌。见[方法令牌](../metadata/method-tokens.md) |

## 环境与完整性

| 标识 | 职责 |
| --- | --- |
| `0x81` | 解密库名和符号，`dlopen` / `dlsym`，缓存函数指针 |
| `0x96` | 按 16 字节块变换的通用解密器 |
| `0x8F` | 读 `/proc/self/cmdline`，查询 uid/gid/tid，创建或复用环境 token，检查路径 owner 与 mode |
| `0x97` | 扫描 `/proc` 中同一 UID 的进程；写代码前 `mprotect`；启动 detached 工作线程 |
| `0x02` | 向 UDP 123 查询时间，再和配置阈值比较 |
| `0x69` | `fork` 子进程探测并等待退出状态 |
| `0x60` | 扫描系统库目录、`/proc` 环境和运行时路径 |
| `0x40` | 检查 `base.apk` 及同目录 split APK。签名顺序：v3.1，然后 v3，然后 v2，然后 JAR/v1 |
| `0x20` | 校验目标路径、ELF 头、`/proc/self/maps` 和 libc 映射 |
| `0x33` | 构造 dex2oat 选项列表，并删除不符合的产物 |
| `0x72` | Unix domain socket 的 `bind` / `listen` / `accept` |
| `0xB0` | 变换一张 sentinel 表 |

## 仅观察到

`0x8E`、`0x6A`、`0x68`、`0x54`、`0x71`、`0x53`、`0xA4`、`0x58`、`0x73`、`0xA0`、`0xB2`。

它们出现在与上表相同的解释器层。会被登记，并且除非 `flags & 0x100`，否则会收到 init/entry 调用。除此之外其含义尚不清楚。
