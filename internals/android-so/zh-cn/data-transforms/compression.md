# Huffman 与 LZ 压缩

压缩的 writer 块使用紧凑 Huffman 表，后接 LZ 风格流。表是 3 字节项组成的森林：一个 u16 符号/子结点字段和一个 u8 码长字段。8 个输入位选择根。最高位（`0x8000`）标记叶子；内部结点存放兄弟对中第一个的下标，再用一个输入位在两者之间选择。

这与 [Windows Huffman/LZ 格式](https://app.gitbook.com/s/fEb9nKPvKsjkPAHMUbOt/data-transforms/compression)是同一套 token 语言。16 位前缀查找可以加速码的前若干位；更长的码再沿树走。

**token 格式。** 第 8–9 位选择模式，第 0–7 位是载荷：

| 模式 | 含义 |
| --- | --- |
| `0x000` | 字面量：写出载荷字节 |
| `0x100` | 计数累加器：把载荷接到大端 pending 值上（本身不输出） |
| `0x200` | 游程填充：把刚写出的 1/2/4 字节单元重复 `pending × payload` 次 |
| `0x300` | LZ 回指：从输出游标后方 `pending + payload` 字节处拷 `payload` 字节 |

只有距离非零、不指向输出起点之前、且请求长度不超过声明目标时，回指才合法。单元宽度不是 1、2 或 4 属于格式错误——解码器不得把这些字节计为已写出。一份实验笔记记录过对异常宽度的 skip-run 子情形；该行为未在跨构建解码器中复现，不属于已接受的格式。

只有当位读取器耗尽允许的输入、且输出恰好达到声明大小时，该块才有效。过早的结束标记、悬空树下标、零宽度叶子，或文档填充之外的尾字节，都是格式错误，而不是部分成功。
