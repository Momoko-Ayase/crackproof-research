# 结构发现与验证

## 为什么一切都要扫描，以及如何避免选错

一个反复出现的事实是：很少有容器对象能在不同构建中保持同一偏移。表的位置会变化，PE32 布局还会应用 `ss_shift`；新版构建会省略标记，无关字节也可能看起来像指针或变换程序。加载器知道编译进自身构建的布局，静态分析则必须从文件中恢复该布局。

不要接受首个匹配。应组合多项独立检查：

- 检查表的形态，例如等于 `info[3]` 的锚点 dword、`(1, 0, info[3], 0)` 条目，以及边界有效的 `(offset, size)` 对。
- 将候选变换程序解析到真正的 `RET`；遇到无效操作码、无效 ModR/M，或只在操作数中偶然出现 `0xC3` 的流就拒绝。
- 要求指针指向当前映像或受保护文件中的有效范围。不能只凭指针看似合理就接受候选。
- 在不保留修改的前提下试解密候选描述符，再检查源范围与目标范围。
- 重放首个压缩节记录，并要求解压结果恰好达到声明大小。只对原始复制记录有效的候选尚未得到验证。
- 布局包含校验和链时，还要核对该链。

稀疏页变换需要单独判断。可识别的 CRT 入口 stub（`48 83 EC ib / E8 / 48 83 C4 ib / E9`，栈立即数相同）在它是唯一一个——包括“不变换”——让解码后的 `call` 与 `jmp` 目标都落在 `.text` 内的候选时，是较强证据。否则应在多个页上比较各候选恢复了多少预期的 `0xCC` 填充，并同时要求相对未改基线的倍率与绝对下限。小幅增长是每页 XOR 255 个位置的噪声，不能据此执行变换。32 位映像用同一套填充测试在 `page+1` 与 `0x8000*(page+1)` 之间选择，或在 `.text` 已是明文时跳过该遍。

若没有候选通过内容检查，应在该阶段停止。输出一个看似正常但已被暗中破坏的 PE，会使后续观察都失去可信度。
