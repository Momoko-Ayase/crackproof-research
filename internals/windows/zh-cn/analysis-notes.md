# 逆向工程笔记

本页汇集对此保护证明有效的方法论，随后如实列出特定机制失效之处。

## 方法论

### 让加载器的日志为己所用

最有效的第一步是开启调试日志：在 `%temp%` 下创建那个随可执行文件而异的 12 位十六进制字符文件夹（在 `CreateFileW` 上下断获知名字），然后运行二进制。每个受保护模块都会自述其启动过程——逐阶段的状态码、缺失的 DLL、被钩函数、地址。结合[运行时行为](runtime-behavior.md#启动序列与状态码)中的状态表，无需任何反汇编即可把任何失败或行为定位到具体阶段。

### 把状态码映射回代码

当日志不够用时，`(code << 4) | 1` 编码把每个状态码变成可在二进制中搜索的 2 字节模式。搜索该字即可找到报告该阶段的那条指令——一张即时的加载器符号表。对磁盘上的加载器 stub 与解密后的阶段缓冲区同样有效。

### 带着正确的预期读加载器

- **不要相信自然的入口点。** 显眼的 stub 是无操作诱饵（计时探测外套着寄存器保存/恢复）。真正的入口是初始化上下文结构的代码——搜索那条唯一的、建立保留上下文寄存器的指令，从那里跟进。
- **预期反汇编失步。** 跳转后的垃圾字节与跳入指令中间的目标让线性扫描失效；反编译器常以 “control flows out of bounds” 收场。静态分析停滞时，改为模拟执行该阶段（CPU 模拟器加 Win32 桩钩子——文件 API 用受保护文件自身的字节应答），捕获其写操作，再把恢复出的原语移植回静态代码。
- **跨构建对比。** 同一家族不同受保护模块的加载器代码逐字节相同；只有数据表不同。跨样本 diff 把表（几百字节）与算法（其余一切）分离——这是看清“什么是按构建配置、什么是代码”的最快途径。

### 正确转储页加密模块

- 单次内存快照只能捕获按需解密的工作集。检查每节的填充率（批量解密的模块每页都有内容；页加密模块呈稀疏的、执行驱动的覆盖），必要时在转储前强制每页缺页。
- 验证转储是解密后的：真实 OEP 处的字节应当是正常的序言（例如 x64 MSVC 构建上的 `48 89 5C 24 08`）。OEP 区域是垃圾或全零说明快照太早——等过初始化。
- 基于缓存管理器的取证提取器（例如 Volatility 的 `dumpfiles`）只能看到 OS 认为在磁盘上的内容；解密后的页位于私有内存，对其不可见。改用基于虚拟地址空间的提取器（按模块列表或按 VAD）。
- 间隔几秒取两份快照做 diff：非零 diff 表明存在后台重加密（状态 `840` 的重加密 pass），零 diff 则确认页面稳定。
- 进程内辅助代码要避开 `A07` 注入线程清扫的时点；清扫前派生的线程可能被杀。清扫完成在调试日志中可见。

### 验证重建映像

报告成功的静态解包仍可能是错的——启发式可能选中貌似合理但并不正确的表。廉价的结构检查能捕获实践中观察到的所有失败模式：

1. `MZ` 与 `PE\0\0` 签名；可选头 magic `0x10B`/`0x20B`；合理的节数。
2. 入口点映射到一个已映射、可执行、非全零的区域（入口桩全零是“留在加密态”的经典症状）。
3. 首个导入描述符的 DLL 名是可读 ASCII 且以 `.dll` 结尾（导入仍是密文是第二个经典症状）。
4. 托管映像：COR20 头 `cb == 0x48` 且元数据流签名 `BSJB`。
5. DLL：存在基址重定位目录。

干净的报告不是正确性证明——但未通过检查是可靠的“已损坏”信号。

## 已观察到的弱点

为完整性与后续研究计，以下机制被证明存在不足：

**VM 检查仅靠配置即可绕过。** 注册表检查只在 BIOS/产品值的*开头*匹配厂商字符串，而至少一家主流虚拟机监控器把其标记放在 BIOS 版本字符串的*末尾*——设置 `SMBIOS.reflectHost = "TRUE"` 即可完全隐藏。VMware 后门探测可用 `monitor_control.restrict_backdoor = "TRUE"` 中和（不安装客户机工具亦可），其他虚拟机监控器则允许直接覆盖 SMBIOS 字符串。

**调试日志是自我说明的加载器。** 方便厂商技术支持的状态码设计，同样把逐阶段的执行轨迹和每阶段一个 2 字节搜索模式交给了分析者。mailslot 通道是加密的，但文件日志不是。

**页加密败给进程内读者。** 按需解密处理器服务来自同一进程任意线程的缺页，因此进程内的辅助代码可以触及每一页并拷出解密字节。反转储涂写是可逆的；在未启用涂写的构建上，页面本来就是干净的。

**内核驱动削弱宿主。** 第一代向任意进程暴露无鉴权的内核 shellcode 执行。第二代的 PID 加密“鉴权”把 `EPROCESS` 写原语授予任何能复现它的程序——一个带签名的 BYOVD——而它设置的 Protected Process 标志既可用内核级手段关掉，也可在其设置前注入来吸收。只有第三代没有给攻击者新的权力。

**防篡改链完全可重算。** 容器中的每种变换都可逆（XOR 链、旋转、置换字节码、内嵌调度表的 CBC-AES），每个校验和都是对已知字节的标准 CRC-32。设计里没有任何必须保存在文件之外的秘密。因此校验和链能发现朴素打补丁，却无法阻止打补丁：修改了 payload 的分析者可以重算每一条链式密钥并重新嵌入结果，加载器会接受它。这条链提高了修改的代价，但并不封顶。

**进程策略检查很粗糙。** 父进程策略（`A03`）从获批父进程启动即可满足；DLL 宿主检查（`A11`）依赖的工件（`peC` 节、混合大小写的 `KeRnEl32.dLl` 导入）只能识别未修改的宿主。

这些并不让保护变得平凡——分层设计仍需真正的工作量才能端到端分析——但每一条都是文档化、可复现的缺口，而非理论推测。
