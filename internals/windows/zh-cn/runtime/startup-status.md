# 启动流程与状态上报

在执行原程序代码前，CrackProof 由宿主桩与手动映射的辅助模块配合执行一套可配置的启动流程，最终在状态 `280` 跳转到 OEP：

```mermaid
flowchart LR
    S200["200..210\n初始化与架构"] --> P1["410..540\n第一阶段检测"] --> KRN["C00..C04 / Bxx\n系统与 Htsysm"]
    KRN --> ASEQ["Axx 调度器\n与 DLL A15"] --> PRE["5D0..5E2, 5C0\n解密准备与导入加载"]
    PRE --> DEC["610, [640], 655, 6E1\n解密与重定位"] --> PG["800..840, 660\n或 800, 830"]
    PG --> EX["[E20..E91]\n驱动设备检测"] --> OEP["280\n跳转至 OEP"]
```

## 启动流程与状态码 <a href="#the-boot-sequence-and-status-codes" id="the-boot-sequence-and-status-codes"></a>

每个启用的阶段都会记录一个 12 位十六进制状态码：

| 状态码 | 阶段含义 |
| --- | --- |
| `200` / `210` | 加载器启动 / 宿主架构检查 |
| `410` | 用户态反调试检查（`IsDebuggerPresent`；实机采样表明商业版 `410` 内不含基于 SEH 的子阶段） |
| `510` | 加载器内存区间的 CRC-32 完整性校验 |
| `520` / `52F` | `NtQueryInformationProcess` 调试状态检查 / 内核调试器检查 |
| `540` | VMware I/O 端口后门探测及 CPU 特性检查 |
| `560` / `561` | 节解密初始化 / 辅助模块选择 |
| `C00` | Windows 最低构建号检查：记录两个 `(0x01A00000 + build)` 双字（当前系统构建号、最低要求构建号） |
| `C01` | 系统启动配置检查（`testsigning`、`disableintegritychecks`） |
| `C02` / `C03` / `C04` | 安装 `Htsysm` 服务（`Htsysm7679`、`Htsysm767901` 或 `Htsysm1B4001`）/ 初始化驱动 / 注册回调或开启 `EPROCESS` 保护与 API hook |
| `A03` | 父进程检查（`explorer.exe` / `cmd.exe`） |
| `A09` | 虚拟机硬件与 BIOS 注册表前缀检查 |
| `A0F` | 注入 DLL 扫描 |
| `A08` / `A04` | 从磁盘拷贝干净的 `ntdll` / `kernel32` `.text` 节（若磁盘上的系统 DLL 本身被篡改，`A04` 还会直接中止进程） |
| `A07` / `A01` | 终止异常外部线程 / 若仍有外部线程残留则中止进程 |
| `A11` | DLL 宿主进程校验（检查宿主 EXE 是否带有 `peC` 节或大小写完全一致的 `KeRnEl32.dLl` 导入项） |
| `A15` | 宿主校验通过后在 `5D0` 之后记录的 DLL 调度标记（无实际检查逻辑；EXE 从不输出该状态码） |
| `B00` / `BD0` / `BE0` | 操作系统兼容性检查 / 检查是否存在 `C:\Windows\msc.log.log` / 旧式 SoftICE 与 Syser 设备名检查 |
| `B21` / `BB0` | 加载旧版驱动辅助模块（`HtsyskNT.dll` / `HtpecmNT.dll`） |
| `5D0` `552` `570` `590` `5B0` `5B1` `598` `5A0` `5E1` `5E2` | 分阶段解密的前置准备步骤 |
| `A06` / `5C0` | 后期 API hook / 加载运行期导入 DLL |
| `610` | 节数据与头部批量解密 |
| `640` | 页面重加密锁定前的可执行页批量解密 |
| `655` / `6E1` | 基址重定位修正 / 尾部节设置 |
| `800` `810` `820` `840` | 页面保护初始化（`800`..`820`）、安装 `KiUserExceptionDispatcher` hook，并将页面重新加密且设为 `PAGE_NOACCESS`（`840`） |
| `830` | 未开启页面加密的原生构建完成页面设置（`800` -> `830`） |
| `660` | 页面加密锁定完成后、进入 `280` 前的交接阶段 |
| `E20` `E40` `E52`..`E59` `E55` `E91` | `1B40` 族系构建中的后期完整性校验与分析工具驱动设备检查 |
| `280` | 最终移交控制权至原始入口点（OEP） |

实测捕获的多模块日志显示各模块保护配置相互独立（参见 [调试日志样本](https://app.gitbook.com/s/L9bXLua8yrIPEUZOHO21/sample-debug-logs)）：开启按需页加密的宿主 EXE 依次执行 `610 -> 640 -> 655 -> 6E1 -> 800..840 -> 660 -> 280`，而同一进程内采用一次性批量解密的原生插件 DLL 则走 `610 -> 655 -> 6E1 -> 800 -> 830 -> 280`。`A` 系列检测由同一个模式驱动的调度器分多轮派发执行。

## 调试日志 <a href="#debug-logging" id="debug-logging"></a>

* **`%temp%\<12 hex>` 目录开关：** 每个受保护模块都会派生一个 12 位十六进制目录名；只要 `%temp%\<12 hex>` 存在且创建时间在约 48 小时以内，加载器就会写出明文跟踪日志（EXE 为 `HHMMSSmmmE-...`，DLL 为 `HHMMSSmmmD-...`）。对 `CreateFileW` 下断点或 hook 即可直接看到其探测的目录路径。
* **`\\.\mailslot\ErrLog-Pec<4 hex>` 邮槽通道：** 另一条独立的诊断通道从 12 位十六进制日志密钥的首个 16 位字 `key` 按 `((key + 1) * 0x3039) mod 0x8003` 派生 `<4 hex>`；当存在对应的邮槽监听端时，会从 `-- Version` 起写出经滚动异或混淆的报告（`state = (derive(key) + 1)^2 ^ ~length; word ^= state; state = ror32(state + i, 7)`）。
* **`AAA-BBB-CCC` 结束状态码：** 两条通道在结束时都会写入一组 9 字符状态码：
  * **`AAA`（3 位十进制数字）：** 正常启动为 `000`；失败时为出错阶段在 104 项阶段表中的十进制序号（从 1 起算，例如 `C03` -> `046`、`A09` -> `048`、`E91` -> `601`）。
  * **`BBB`（3 位大写十六进制数字）：** 出错阶段内记录到的首个子阶段码。
  * **`CCC`（3 位大写十六进制数字）：** `BBB` 尚未置位时记录到的首个原因/错误码（实测样本可见 `046-019-01F`、`048-012-002`、`601-000-008`）。

{% hint style="info" %}
**在内存中定位状态码上报点。** 日志辅助函数通过 `ECX` 接收打包后的 12 位代码，低 4 位用于区分类型：阶段状态码为 `1`（`(code << 4) | 1`，例如 `0xC01` -> `0xC011`），`CCC` 原因码为 `3`（`(code << 4) | 3`），`BBB` 子阶段码为 `5`（`(code << 4) | 5`）。宿主模块自身的加载器节内仅包含核心引导状态码（`200`、`560`、`590`、`5A0`、`5E1`、`5E2`、`800`，且第一阶段的立即数在执行后会被擦除）；`410`/`510`/`520`/`540`、`Cxx` 与 `Axx` 立即数均位于手动映射的辅助 DLL（`HtpecIt`、`dm` 等）内部。
{% endhint %}
