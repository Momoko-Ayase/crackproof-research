# 启动序列与状态报告

受保护二进制的首个执行线程属于 CrackProof，而非程序。加载器沿固定管线行进：环境检查、反分析清扫、内核驱动与子模块设置，然后是[加载与节恢复](../loading-and-pe-repair/loading/README.md)中的分阶段解密，随后可选地把刚解密的内容重新加密，最后才跳转到原始入口点（OEP）。本页描述在运行时观察到的这条管线。

## 启动序列与状态码

加载器以 12 位**状态码**报告进度，大致每阶段一个。列表并不完整。各阶段按构建可配置，因此任何给定二进制只显示其中一个子集：

| 代码 | 阶段 |
| --- | --- |
| `200` | 启动 |
| `210` | 主机架构检查 |
| `410` | 用户态反调试开始 |
| `510` | 加载器某块内存的 CRC-32 |
| `520` | `NtQueryInformationProcess` 检查 |
| `52F` | 内核调试器检查 |
| `540` | VMware 后门探测（和/或 CPU 特性标志） |
| `560` | 代码节解密初始化 |
| `561` | 选择支持模块（部分新构建不再使用） |
| `C00` | OS 最低版本检查 |
| `C01` | 启动选项检查（`testsigning`、`disableintegritychecks`） |
| `C02` | 安装 Htsysm 驱动服务。日志会打出设备名（`Htsysm7679`、`Htsysm767901` 或 `Htsysm1B4001`）以及 `C:\Windows\System32` 下的磁盘驱动文件名——后者是按部署而定的工件，不是格式常量。 |
| `C03` | 初始化较新 Htsysm 驱动 |
| `C04` | 设置 Protected Process 标志；安装钩子 |
| `A0F` | 注入 DLL 检查 |
| `A09` | 经硬件注册表字符串的 VM 检查 |
| `A08` | 从磁盘拷贝干净的 ntdll/kernel32 代码到内存 |
| `A04` | 同上，磁盘副本被补丁则中止 |
| `A07` | 终止注入线程 |
| `A01` | 发现注入线程则中止 |
| `A03` | 父进程检查（`cmd.exe` / `explorer.exe`） |
| `A11` | 对 DLL：检查宿主进程（`peC` 节，或来自 `KeRnEl32.dLl` 的导入） |
| `A15` | 对 DLL：在 `5D0` 之后记录的宿主信任标记；自身不带检查体，只在之前的检查链通过后出现 |
| `B00` | OS 兼容版本检查 |
| `B21` | 加载 `HtsyskNT.dll`（旧驱动路径） |
| `BD0` | 确保 `C:\Windows\msc.log.log` 不存在 |
| `BE0` | SoftICE/Syser 调试器检查 |
| `BB0` | 加载 `HtpecmNT.dll`（旧驱动路径） |
| `5D0` `552` `570` `590` `5B0` `5B1` `598` `5A0` `5E1` `5E2` | 解密前奏阶段 |
| `A06` | 启动后期 API 钩子（若记入日志） |
| `5C0` | 加载运行时 DLL（缺失者记入日志） |
| `610` | 解密 PE 头 |
| `640` | 解密可执行页 |
| `655` | 重定位 |
| `6E1` | 收尾；部分构建会重新加密一段可执行范围 |
| `800` `810` `820` | 页加密准备 |
| `840` | 安装异常处理钩子；重新加密可执行页 |
| `E20` `E40` `E52`–`E59` | 部分 `1B40` 家族构建的后期完整性阶段 |
| `E55` `E91` | 针对分析工具驱动设备名的检查 |
| `660` | 页加密准备之后、跳转 OEP 之前的阶段 |
| `280` | 跳转到 OEP |

观察到的序列证实特性是按模块配置的：在一个作品中，宿主 EXE 记录 `640 … 840`（批量解密后接页重加密），而同一进程中的原生插件 DLL 从 `610`（节解密）直接到 `655`——只批量解密一次，从不做页加密。

`A` 系列检查并非硬连在阶段遍历器里。它们由同一个调度函数驱动，遍历器以不同模式多次调用它；每次调用只运行构建选项标志选中的子集。受保护 DLL 以自己的模式驱动。这就是为什么 DLL 日志在 `5D0` 前是 `A09`、`A11`、在其后是 `A15`，而同一作品的宿主日志在 `5D0` 前是 `A09` `A0F` `A08` `A07`、在其后是 `552` `570`。

`C00` 一行记录两个 dword。每个都是 `0x01A0` 加上一个 Windows 构建号：前者是主机构建，后者是可接受的最低构建。已观察的下限对应 Windows 10。

一份已观察的 `Htsysm1B4001` 日志在 `C04` 列出的钩子更少，并继续打出后面的 `E` 段，包括 `E55` 与 `E91` 的设备名检查。

## 调试日志

当 `%temp%` 下存在某个特定文件夹时，加载器会为每个受保护模块写入一份详细调试日志。文件夹名为 12 个十六进制字符，随可执行文件不同而不同。获知该名称最直接的办法是在 `CreateFileW` 上下断点或钩子。文件夹的创建时间必须在大约两天以内；更旧的文件夹会留在原地，该次运行不写日志。

日志行携带[启动序列与状态码](#启动序列与状态码)中列出的状态码，偶尔还有自由文本诊断（缺失的 DLL 名、被钩函数列表、地址）。

第二个通道把加密日志发往 mailslot `\\.\mailslot\ErrLog-Pec<number>`。两个通道共享一种 9 位错误格式 `AAA-BBB-CCC`：失败时的恢复状态码、一个子阶段，以及第三个字段。已观察的取值包括 `046-019-01F`（内核回调被关闭）、`048-012-002`（Hyper-V）和 `601-000-008`（分析工具驱动）。

{% hint style="info" %}
**在二进制中定位阶段。** 状态码经由一个辅助函数写出，编码为 16 位值 `(code << 4) | 1`。在写日志处下断，然后在二进制中按字节搜索该字（例如 `0xC01` → `11 C0`），即可直接落在发出该阶段的代码上。这是目前已知的、把状态码对应到加载器代码的最快办法。
{% endhint %}
