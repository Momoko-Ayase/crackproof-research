# 已知设计局限

对各 Windows 构建族系的静态分析与实机测试表明，其保护架构存在以下八项可稳定复现的设计局限：

* **仅匹配前缀的虚拟机注册表检测（`A09` 与 `540`）：** `A09` 只检查三个 BIOS/系统注册表值是否以特定厂商字符串开头（若虚拟化标识位于 `SystemBiosVersion` 末尾，或配置了 `SMBIOS.reflectHost = "TRUE"`，均不会命中），而 `540` 可通过配置 `monitor_control.restrict_backdoor = "TRUE"` 关闭。
* **明文 `%temp%` 跟踪日志机制：** 只要在 `%temp%` 下建好对应的 12 位十六进制目录，商业版加载器自身就会以明文输出阶段编号、模块基址、缺失导入项、已 hook 的 API 以及 `AAA-BBB-CCC` 失败定位码。
* **不区分调用线程的按需页解密：** `HtdpStub2.dll` 的 `KiUserExceptionDispatcher` hook 会为当前进程内的任意线程解密触发异常的页面；主动遍历触发全部受保护页面缺页（并还原可选的 `scribble` 涂抹掩码），即可完整恢复可执行节明文。
* **旧版内核驱动的攻击面：** 第 1 代驱动（`HtsysmNT`）暴露了无鉴权的 Ring 0 Shellcode 执行接口；第 2 代驱动（`Htsysm7679`）仅靠可逆的 PID 变换保护其 `offset < 0x1000` 的 `EPROCESS` 掩码写 IOCTL（已签名版本可直接用作 BYOVD 提权原语）。仅第 3 代驱动（`0xAA02` `ObRegisterCallbacks`）不再向用户态调用方开放内核提权或改写原语。
* **无外部密钥的自包含校验链：** 所有密码轮密钥、哈夫曼表与字节码桩均随容器一同分发，各阶段密钥完全由标准 CRC-32 与确定性算术运算派生，不涉及外部非对称密钥，因此修改载荷后可直接重算后续各阶段的派生密钥。
* **可伪造的 `A03` 与 `A11` 进程标记：** `A03` 仅核对父进程文件名（`explorer.exe` / `cmd.exe`），`A11` 则靠节名 `peC` 或大小写固定的导入字符串 `KeRnEl32.dLl` 识别 CrackProof 宿主 EXE，并未采用密码学宿主认证。
* **过短的内存宿主特征印记：** 部分构建在加载后还会检查宿主镜像中的附加字节标记，但仅比对固定位置的少数几个字节，并未对宿主代码计算完整哈希。
* **较窄的用户态反调试覆盖面：** 实机采样显示，商业版 `410`/`520` 主要依赖 `IsDebuggerPresent` 与 `NtQueryInformationProcess`（`410` 内部不含基于 SEH 的反调试子阶段），`A0F` 也只是按固定名单扫描常见注入 DLL 名称。
