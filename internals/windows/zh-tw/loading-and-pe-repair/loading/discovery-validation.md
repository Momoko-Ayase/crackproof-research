# 結構發現與驗證

## 結構發現與錯誤候選的排除

一個反覆出現的事實是：很少有容器對象能在不同構建中保持同一偏移。表的位置會變化，PE32 佈局還會應用 `ss_shift`；新版構建會省略標記，無關字節也可能看起來像指針或變換程序。加載器知道編譯進自身構建的佈局，靜態分析則必須從文件中恢復該佈局。

不要接受首個匹配。應組合多項獨立檢查：

- 檢查表的形態，例如等於 `info[3]` 的錨點 dword、`(1, 0, info[3], 0)` 條目，以及邊界有效的 `(offset, size)` 對。
- 將候選變換程序解析到真正的 `RET`；遇到無效操作碼、無效 ModR/M，或只在操作數中偶然出現 `0xC3` 的流就拒絕。
- 要求指針指向當前映像或受保護文件中的有效範圍。不能只憑指針看似合理就接受候選。
- 在不保留修改的前提下試解密候選描述符，再檢查源範圍與目標範圍。
- 重放首個壓縮節記錄，並要求解壓結果恰好達到聲明大小。只對原始複製記錄有效的候選尚未得到驗證。
- 佈局包含校驗和鏈時，還要核對該鏈。

稀疏頁變換需要單獨判斷。可識別的 CRT 入口 stub（`48 83 EC ib / E8 / 48 83 C4 ib / E9`，棧立即數相同）在它是唯一一個（包括「不變換」）讓解碼後的 `call` 與 `jmp` 目標都落在 `.text` 內的候選時，是較強證據。否則應在多個頁上比較各候選恢復了多少預期的 `0xCC` 填充，並同時要求相對未改基線的倍率與絕對下限。小幅增長是每頁 XOR 255 個位置的噪聲，不能據此執行變換。32 位映像用同一套填充測試在 `page+1` 與 `0x8000*(page+1)` 之間選擇，或在 `.text` 已是明文時跳過該遍。

若沒有候選通過內容檢查，應在該階段停止。輸出一個看似正常但已被暗中破壞的 PE，會使後續觀察都失去可信度。
