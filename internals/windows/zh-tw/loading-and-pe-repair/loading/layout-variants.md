# PE32、DLL 與無標記佈局

## 32 位（PE32）流程

32 位家族共享頭部/payload 階段，隨後完全分叉：不同的錨點、額外一代階段，以及在 64 位流程取固定值處使用爆破參數。

**`tbl` 錨點。** 在 `info[6]` 附近的 shell 區掃描一個等於 `info[6]`、後隨合理 shell 大小的 dword；錨點在其前 `0x88` 字節。導入/資源目錄從 `tbl + 0xBC/0xC8/0xCC` 恢復；**頭部校驗和**（對 `tbl + 0x58` 處描述符鏈逐項 `calculate_checksum` 的異或）成為之後每個階段密鑰的組成部分。注意其含義：階段密鑰依賴*保護前原始 PE 頭*的校驗和。

**SecondStage。** `tbl + 0x98` 處的 `(offset, size)` 對以 `ss_key = header_checksum ^ first_stage_cs ^ second_stage_key`（移位 21）解出。常量 `ss_shift = ss_size − 0xBC0` 隨後參數化*每一個*後續偏移——一種對整個階段佈局的按構建置換。原生 DLL 帶有保護層添加的 BaseReloc 數據目錄（原始頭部沒有），因此頭部校驗和只有把該項清零後才匹配；兩種變體都試，ThirdStage 指針通過校驗者勝出。

**ThirdStage。** 移位量未被記錄；在 `[19, 21, 17, 23, 15, 25, 13, 11]` 上爆破，接受輸出中含 info 表簽名（一個 `1`/`0x11` 項後隨 `2` 項且地址合理）的移位量。四個密鑰偏移位於 info 表前 `0x58` 字節，解密方式同 64 位流程。

**Fourth/Fifth/Seventh。** 分別從 `dp_base + 0x40/0x50/0x70` 處的四元組解出，密鑰形如 `header_checksum ^ crc32(前一区域) ^ advance_key(种子)`，種子取自剛解密的前一階段。`advance_key` 的輪數不是定值：它等於 `dp_base` 處四槽位、16 字節描述符表中處於前導位置的活動助手數——槽位在其尺寸 dword（`+4`）大於 4 時為活動，遇到第一個空槽即停止計數，即使後面的槽位非空。Seventh 階段內含首個**字節碼 stub**（先向後、失敗再向前地 LFSR 掃描定位）。

**EighthStage 及其密鑰搜索。** Eighth 階段密鑰同樣不被存儲：候選項從 stub 周圍的間隙啟發式收集（區域末端間隙 `0xD0…0x100`、stub 相對間隙，以及對非可打印 dword 的線性掃描），各經 `advance_key` 推進，輪數按同一活動助手規則取自 `dp_base + 0x80` 處的表，再逐個代入完整的階段解密複合操作。勝者是結果**能乾淨解壓且指針落在映像內**的候選——Huffman 解碼器提供了明確的成功條件。

**配置簇。** Eighth 階段持有最終的表簇，相對一基址取固定偏移：導入表 `+0x18`、文件校驗鏈 `+0x30`、節描述符 `+0x40`、清零列表 `+0x48`。經典構建在該基址戳有 dword `0x00007679`（一個同時出現在驅動名中的構建版本值——見 [Htsysm 內核組件](../../runtime/kernel-components.md)），並把文件數據**字節碼 stub** 放在 `+0x4B4`；緊湊階段把 stub 放得更靠近簇，固定的 `+0x4B4` 槽位會越過它們。因此定位只要求到 `+0x4C` 為止的配置字段落在階段內：有戳構建按戳匹配，無戳構建按校驗鏈槽位的形狀定位（指針恰在 `info[3]` 之後、帶一個小的 16 對齊尺寸），而 stub 本身靠試解證明，絕不按偏移假定。

**文件解密器，需證明。** 文件數據字節碼 stub 不信任最近的掃描命中：每個候選都通過在快照上重放首個*壓縮*塊的完整變換（拷貝 → AES → 翻譯 → 解壓）並要求解壓成功來驗證。真實構建中確實存在能解碼出錯誤翻譯表的巧合 LFSR 形塊。在一個已觀察的 32 位家族中，它就位於真 stub 之前幾十字節，因此試解-驗證是唯一安全的選擇。

**輸出。** 32 位流程以節表修補、代碼頁擾動（公式由 `0xCC` 統計選出）、導入重建（EXE 附帶 `.kmiat` 搬遷）、TLS 重建，以及把 RVA 佈局映像壓實迴文件對齊 PE 的收尾壓縮結束。詳見 [PE 重建](../pe-reconstruction/README.md)。

## 專用 DLL 佈局（較舊 DLL）

較舊的受保護 DLL 佈局運行同一套原語，但把配置塊釘在**固定錨點** `keys[6] + 5592`——無需掃描。所有字段都是它的固定偏移：

| 錨點偏移          | 內容                            |
| ------------- | ----------------------------- |
| `+4` / `+8`   | 導入目錄 Size / RVA               |
| `+20`         | 主描述符加密密鑰                      |
| `+40` / `+44` | 資源目錄 RVA / Size               |
| `+48` / `+56` | 校驗和描述符（checksum2 / checksum1） |
| `+120`        | 主描述符 → 主階段表                   |
| `+184`        | XOR 累加校驗鏈                     |

階段鏈隨後運行：主表（移位 21）→ `+3632` 處的次級表（移位 19，密鑰為 `+3444` 處的 dword）→ `+9248` 處的兩個重定位塊（kind `1`/`0x11`：對描述符就地跑 rotate-by-3 密碼；kind `2`：一個 `(src, size, dst, verify)` 拷貝遍歷，其 16 字節條目以 rotate-by-2 密碼解密）→ `+9160` 處的四個解壓參數 → `+3712/+3728/+3760/+3840` 處的代碼塊 1–4，各自帶校驗和鏈密鑰（含四輪與三輪三角數累加）→ 兩個字節碼 stub（`addr4 + 3200` 與 `metadata + 88`）→ `addr5 + 11976` 處的節描述符遍歷。

兩個該家族獨有的細節：

* 節描述符存儲 `(dest, size, src, expected_crc)`；磁盤基址為 `section_image_base = 4095 − u32@0x1080`，僅當 `size != expected_crc` 時解壓。（該字段被複用為解壓後尺寸，並非 CRC。）
* PE 頭元數據以 `keys[3] + 16` 處一個 656 字節 blob 交付，用位置密鑰的 rotate-by-2 密碼（與 [byte\_rotate2](../../data-transforms/rolling-and-rotation.md#三重字節旋轉密碼) 同一構造）解密：入口點在 blob 內 `0x10` 處，完整的 128 字節數據目錄數組在 `0x20` 處；二者都被寫入 PE 頭（`pe + 40` 與 `pe + 136`）。

此家族中的託管 DLL 還會在節恢復之前，從原文件預填含 CLR 頭的節，並在之後重拷 COR20 區域——CLR 結構是被保留而非加密的。

## 無標記佈局（較新 64 位構建）

較新構建去掉了兩個 stage-5 標記，walk3/walk4/walk5 槽位因此無法由標記推出。佈局改為結構化發現：

1. **收集最終階段內全部 LFSR 包裹的字節碼塊**（逐個試解碼並解析候選，每次命中後逐字節前進——假陽性可能緊貼真 stub 之前，固定步長跳過會越過真身）。
2. **選文件解密器**：取校驗鏈指針（`块 − 0x58`）落在 `info[3]` 之後、正距離最小者。
3. **找節描述符表**：掃描 stub 附近的指針槽，用 `trial_byte_rotate2` 試解其目標，直到某個解析為合理的 `(src, src_len, dst, dest_len)` 描述符。
4. **證明選擇**：在所選 stub 下重放首個壓縮塊的完整變換，要求解壓成功。

與標記佈局的其他差異：只用於校驗的 walk3 鏈不存在；導入從 PE 導入目錄而非 walk5 指針表重建；入口點/數據目錄塊使用 “Layout B” 擺放；託管元數據在代碼頁擾動*之後*才恢復，因為 CLR 結構位於 `.text` 內但不是被擾動的代碼（見[重定位、頁變換與 CLR 數據](../pe-reconstruction/relocations-managed.md#代碼頁擾動排在最後)）。這些構建還保留其重定位表與 ASLR 標誌，因此它們不是 `/FIXED`。
