# 頭、節與零填充範圍

節內容加密只是保護層工作的一半。PE 結構本身也被拆解：Windows 加載器需要的字段被移除或加密，由運行時加載器在恢復後重新創建。本頁逐項說明這些變換，以及運行時如何把它們還原回來。它面向兩類讀者：靜態分析受保護文件的人（結構不在 PE 工具期待的位置），以及驗證重建映像的人（每項變換都有一個必須已發生的還原步驟）。

## 節表變成內存佈局

普通 PE 通過節表把文件偏移映射到 RVA。受保護映像存儲的則是加載器在內存中產出的佈局：每節的 `SizeOfRawData` 設為其 `VirtualSize`，`PointerToRawData` 設為其 `VirtualAddress`。節內容於是統一按 RVA 尋址，磁盤與內存一致。

32 位家族在最後一步加上逆變換：把 RVA 佈局的映像壓實迴文件對齊的 PE——頭部位於 `0x400`，各節按 `0x200` 文件對齊連續排布，裁掉每節原始數據尾部的零串，並重寫 `FileAlignment`/`SizeOfHeaders`。

## 入口點與數據目錄被加密

`AddressOfEntryPoint` 與全部十六個 `IMAGE_DATA_DIRECTORY` 項加密存放在映像基址（`info[3]`）附近，以[位置密鑰字節密碼](../../data-transforms/rolling-and-rotation.md#三重字節旋轉密碼)包裹。每種位寬有兩種擺放：

| 家族                    | 塊起始              | 入口點     | 數據目錄    | 加密長度     |
| --------------------- | ---------------- | ------- | ------- | -------- |
| 64 位 “Layout A”（標記佈局） | `info[3] + 0x40` | `+0x40` | `+0x50` | 144 字節   |
| 64 位 “Layout B”（無標記）  | `info[3] + 0x20` | `+0x20` | `+0x30` | 144 字節   |
| 32 位 “Layout A”       | `info[3] + 0x40` | `+0x40` | `+0x50` | 144 字節   |
| 32 位 “Layout B”       | `info[3] + 0x10` | `+0x20` | `+0x30` | 0x290 字節 |

64 位標記構建上擺放靠探測：試解候選入口點之後的 dword，檢查是否等於映像基址。32 位上選擇器是 `info[3] + 0x10` 處的 dword（大於 `0x10000` → Layout B）。該塊被**臨時**解密（入口點寫入 `pe + 40`，128 字節目錄寫入 `pe + 136`（64 位）或 `pe + 0x78`（32 位）），隨後加密字節被複原：受保護文件即使在其他一切解包完成後仍保持該區域加密，因此正確的重建結果在 `info[3] + ep_off` 處依然顯示密文。

運行時加載器不直接使用的 PE 頭字段在磁盤頭部保持抹除狀態，直到這次還原運行——這就是為什麼 PE 工具在受保護文件上顯示垃圾入口點（常見的小值如 `0x1B5C`）。

託管映像在該塊中把入口點存為 0。真正的入口是 CLR 頭的屬性，不是 PE 的。解密值為 0 時，重建應保留受保護頭裡的入口點；寫成 0 會把映像入口指到 DOS 頭。

## 清零列表

並非原始映像的每個區域都被存儲：`.bss` 類區域以清零列表交付——64 位的 walk4 第二條鏈、32 位的 zero-list 簇槽位，以及專用 DLL 佈局的收尾清零鏈。每項是一個 `(dst, size)` 對，以與節描述符相同的 16 字節位置鏈解密，在解壓之後（32 位：之前）清零。
