# 實測架構限制

透過對各個 Windows 組建家族進行靜態分析與實機測試，可重現以下八項架構層面的設計限制：

* **僅比對字串開頭的 VM 登錄檔檢查（`A09` 與 `540`）：** `A09` 只檢查三個 BIOS／系統登錄檔數值的字串前綴是否符合廠商字串（若虛擬化平台將識別字放在 `SystemBiosVersion` 尾端，或設定了 `SMBIOS.reflectHost = "TRUE"`，便不會命中）；至於 `540` 後門埠探測則只要設定 `monitor_control.restrict_backdoor = "TRUE"` 即可停用。
* **明文 `%temp%` 追蹤機制：** 只要在 `%temp%` 下建立對應的 12 位十六進位資料夾，商用版載入器本身就會以明文輸出各階段編號、模組載入位址、缺少的匯入項目、遭 hook 的 API 以及 `AAA-BBB-CCC` 失敗狀態碼。
* **行程內隨選分頁解密服務：** `HtdpStub2.dll` 安裝的 `KiUserExceptionDispatcher` hook 會替同一行程內的任何執行緒解密觸發存取違規的分頁；只要主動觸發所有受保護分頁完成解密（並還原選用的 `scribble` 遮蔽），即可取回完整的可執行區段。
* **舊世代核心驅動程式的攻擊面：** 第 1 代（`HtsysmNT`）開放了未經驗證的 Ring-0 shellcode 執行功能，而第 2 代（`Htsysm7679`）針對 `offset < 0x1000` 範圍修改 `EPROCESS` 的遮罩寫入 IOCTL 僅靠一套可逆的 PID 加密把關（使具備有效簽章的舊版驅動可被當作 BYOVD 提權原語利用）。直到第 3 代（`0xAA02` `ObRegisterCallbacks`）才不再向使用者模式呼叫端提供可遭濫用的提權原語。
* **無外部金鑰的封閉式 CRC 金鑰推導鏈：** 所有加密排程、霍夫曼表與位元組碼 stub 都隨容器一併存放，且各階段金鑰皆由標準 CRC-32 與確定性算術推導而來，完全不涉及外部非對稱金鑰；因此若修改酬載內容，後續各階段的金鑰皆可重新推算得出。
* **可偽造的 `A03` 與 `A11` 行程特徵標記：** `A03` 僅比對父行程執行檔名稱（`explorer.exe` / `cmd.exe`），而 `A11` 僅憑區段名稱 `peC` 或精確大小寫的匯入字串 `KeRnEl32.dLl` 來辨識 CrackProof 宿主 EXE，並未採用密碼學機制驗證宿主身分。
* **極短的記憶體內宿主戳記：** 部分組建雖會額外檢查宿主映像載入後的特定位元組標記，但僅比對固定少數幾個位元組，並未對宿主程式碼計算雜湊。
* **涵蓋範圍有限的使用者模式反除錯：** 動態擷取分析顯示商用版 `410` / `520` 僅依賴 `IsDebuggerPresent` 與 `NtQueryInformationProcess`（`410` 內部並無 SEH 反除錯子階段），且 `A0F` 也只掃描一份固定的常見注入 DLL 名稱清單。
