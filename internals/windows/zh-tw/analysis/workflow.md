# 分析流程

這些步驟用於定位階段、解釋調試日誌，並檢查重建映像。

## 方法論

### 讓加載器的日誌為己所用

最有效的第一步是開啟調試日誌：在 `%temp%` 下創建那個隨可執行文件而異的 12 個十六進制字符文件夾（在 `CreateFileW` 上下斷獲知名字），然後運行二進制。文件夾的創建時間必須在大約兩天以內，否則該次運行不寫日誌。每個受保護模塊都會自述其啟動過程——逐階段的狀態碼、缺失的 DLL、被鉤函數、地址。結合[啟動序列與狀態報告](../runtime/startup-status.md#啟動序列與狀態碼)中的狀態表，無需任何反彙編即可把任何失敗或行為定位到具體階段。

### 把狀態碼映射回代碼

當日志不夠用時，`(code << 4) | 1` 編碼把每個狀態碼變成可在二進制中搜索的 2 字節模式。搜索該字即可找到報告該階段的那條指令——一張即時的加載器符號表。對磁盤上的加載器 stub 與解密後的階段緩衝區同樣有效。

### 帶著正確的預期讀加載器

- **不要相信自然的入口點。** 顯眼的 stub 是無操作誘餌（計時探測外套著寄存器保存/恢復）。真正的入口是初始化上下文結構的代碼——搜索那條唯一的、建立保留上下文寄存器的指令，從那裡跟進。
- **預期反彙編失步。** 跳轉後的垃圾字節與跳入指令中間的目標讓線性掃描失效；反編譯器常以 “control flows out of bounds” 收場。靜態分析停滯時，改為模擬執行該階段（CPU 模擬器加 Win32 樁鉤子——文件 API 用受保護文件自身的字節應答），捕獲其寫操作，再把恢復出的原語移植回靜態代碼。
- **跨構建對比。** 同一家族不同受保護模塊的加載器代碼逐字節相同；只有數據表不同。跨樣本 diff 把表（幾百字節）與算法（其餘一切）分離——這是看清“什麼是按構建配置、什麼是代碼”的最快途徑。

### 正確轉儲頁加密模塊

- 單次內存快照只能捕獲按需解密的工作集。檢查每節的填充率（批量解密的模塊每頁都有內容；頁加密模塊呈稀疏的、執行驅動的覆蓋），必要時在轉儲前強制每頁缺頁。
- 驗證轉儲是解密後的：真實 OEP 處的字節應當是正常的序言（例如 x64 MSVC 構建上的 `48 89 5C 24 08`）。OEP 區域是垃圾或全零說明快照太早——等過初始化。
- 基於緩存管理器的取證提取器（例如 Volatility 的 `dumpfiles`）只能看到 OS 認為在磁盤上的內容；解密後的頁位於私有內存，對其不可見。改用基於虛擬地址空間的提取器（按模塊列表或按 VAD）。
- 間隔幾秒取兩份快照做 diff：非零 diff 表明存在後臺重加密（狀態 `840` 的重加密 pass），零 diff 則確認頁面穩定。
- 進程內輔助代碼要避開 `A07` 注入線程清掃的時點；清掃前派生的線程可能被殺。清掃完成在調試日誌中可見。

### 驗證重建映像

報告成功的靜態解包仍可能是錯的——啟發式可能選中貌似合理但並不正確的表。廉價的結構檢查能捕獲實踐中觀察到的所有失敗模式：

1. `MZ` 與 `PE\0\0` 簽名；可選頭 magic `0x10B`/`0x20B`；合理的節數。
2. 入口點映射到一個已映射、可執行、非全零的區域（入口樁全零是“留在加密態”的經典症狀）。
3. 首個導入描述符的 DLL 名是可讀 ASCII 且以 `.dll` 結尾（導入仍是密文是第二個經典症狀）。
4. 託管映像：COR20 頭 `cb == 0x48` 且元數據流簽名 `BSJB`。
5. DLL：存在基址重定位目錄。

乾淨的報告不是正確性證明——但未通過檢查是可靠的“已損壞”信號。
