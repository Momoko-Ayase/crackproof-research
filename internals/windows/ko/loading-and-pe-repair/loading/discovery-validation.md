# 구조적 탐색 및 검증

빌드마다 스테이지 크기가 달라지고(PE32의 `ss_shift`, 64비트의 `anchor_extra`) 최신 64비트 빌드는 고정된 Stage 5 마커를 생략하므로, 정적 복구 과정에서는 작업 이미지를 수정하기 전에 모든 오프셋, 시프트, 시드 후보를 단계별로 검증합니다.

* **앵커 및 테이블 불변 조건:** 스테이지 디스크립터를 풀기 전에 `u32@anchor == info[3]`, Stage 2 `table_start`의 `(1, 0, info[3], 0)` 시그니처, 그리고 `{offset, size}`가 이미지 범위 내에 들어오는지 먼저 확인합니다.
* **엄격한 바이트코드 VM 문법:** 96바이트 LFSR 후보 슬롯을 `0xC3`(`RET`)이 나올 때까지 파싱하며, `AL` 레지스터 이외의 `ModR/M` 인코딩(`mod != 3`, `rm != 0` 또는 `reg > 1`)은 모두 후보에서 제외합니다. 실제 스텁 앞에 오탐 후보가 나타날 수 있는 구간에서는 스캔 오프셋을 1바이트씩 이동합니다.
* **원본을 유지하는 디스크립터 사전 검사:** `trial_byte_rotate2`로 원본 버퍼를 수정하지 않고 후보 포인터 대상을 확인해 `src + section_data_file_base`가 파일 범위 안에 있고 `dst + plain_len`이 `SizeOfImage` 범위 안에 들어오는지 검증합니다.
* **첫 번째 압축 블록 실제 해제 검증:** 단순 복사 블록만 보고 바이트코드 스텁이나 `EighthStage` 시드를 채택하지 않습니다. 반드시 첫 번째 압축 블록에 AES 복호화, 바이트코드 변환, `decompress`를 실제로 적용해 허프만 트리 탐색이 유효하고 `written == plain_len`이 정확히 성립하는지 확인합니다.
* **3단계 `.text` 페이지 스크램블 (`dd8`) 선택 규칙:**
  1. 64비트 이미지에서는 먼저 18바이트 CRT 엔트리 스텁(`48 83 EC ib / E8 rel32 / 48 83 C4 ib / E9 rel32`)에 대해 원본 유지(`unchanged`), `shift 0`, `shift 15` 세 가지 모드를 시험하고, `call` 및 `jmp` 대상 주소가 모두 `.text` 내부에 들어오는 유일한 모드를 선택합니다.
  2. CRT 엔트리 스텁으로 판별되지 않는 64비트 이미지에서는 `.text` 내 페이지에서 `0xC3`(`RET`) 뒤에 `>= 4`바이트의 `0xCC` 패딩이 이어지는 구간의 길이를 합산해, 원본 대비 증가폭이 `>= 8`인 모드를 선택합니다.
  3. 64비트에서 모든 `RET + int3` 점수가 `0`일 때만(32비트에서는 `page + 1` 대 `0x8000 * (page + 1)` 비교 시 항상 적용), 변환으로 값이 바뀐 위치 중 `0xCC`가 되는 바이트 수를 세어 원본 기준치의 2배 이상(`>= 2x`)이면서 `8`바이트 이상(`>= 8`)일 때만 `.text`를 수정합니다.

어느 단계에서든 모든 후보가 검증에 실패하면 불완전하게 디코딩된 PE를 출력하지 않고 명시적인 오류와 함께 복구를 중단합니다.
