# 構造探索と妥当性検証

ステージサイズはビルドごとに変化し（PE32 の `ss_shift`、64 ビットの `anchor_extra`）、さらに新世代の 64 ビットビルドには Stage 5 の固定マーカーが存在しません。そのため静的復元では、作業イメージを書き換える前にすべてのオフセット・シフト量・シード候補を検証します。

* **アンカーおよびテーブルの不変条件：** いずれのステージ記述子を展開する際も、事前に `u32@anchor == info[3]`、Stage 2 の `table_start` における `(1, 0, info[3], 0)`、および `{offset, size}` がイメージ境界内に収まることを確認します。
* **バイトコード命令の厳密な検証：** 96 バイトの LFSR スロット候補を `0xC3`（`RET`）に到達するまでパースし、`AL` 以外を対象とする `ModR/M` エンコーディング（`mod != 3`、`rm != 0`、または `reg > 1`）をすべて棄却します。本物のバイトコードスタブの手前に偽陽性が現れ得る箇所では、1 バイト刻みでスキャンを進めます。
* **非破壊の記述子先読み：** ポインター候補の参照先を `trial_byte_rotate2` で検査し、`src + section_data_file_base` がファイル範囲内、`dst + plain_len` が `SizeOfImage` 範囲内にそれぞれ収まることを確認します。
* **最初の圧縮ブロックによる実証：** 非圧縮コピーのブロックだけでバイトコードスタブや `EighthStage` シードを確定せず、必ず最初の圧縮ブロックに対して AES 復号 + バイトコード変換 + `decompress` を試行し、有効なハフマン木走査を経て `written == plain_len` となることを要求します。
* **3 段階の `.text` ページスクランブル（`dd8`）選択：**
  1. 64 ビットイメージでは、`unchanged`、`shift 0`、`shift 15` の 3 モードそれぞれについて 18 バイトの CRT エントリスタブ（`48 83 EC ib / E8 rel32 / 48 83 C4 ib / E9 rel32`）を検査し、`call` と `jmp` の両方のターゲットが `.text` 内に収まるモードが一意に定まればそれを選択します。
  2. 上記で決まらない 64 ビットイメージでは、`.text` 内部ページにおいて `0xC3`（`RET`）の直後に `4` バイト以上の `0xCC` パディングが続くランの総長をスコア化し、無変換のベースラインに対して `8` 以上の正の差分が得られるモードを選択します。
  3. 64 ビットですべての `RET + int3` スコアが `0` だった場合のみ（および 32 ビットで `page + 1` と `0x8000 * (page + 1)` を比較する場合は常に）、変換によって値が変化した位置のうち `0xCC` になったバイト数を数え、ベースラインの `2` 倍以上かつ `8` 個以上のヒットという両条件を満たすときに限り `.text` を更新します。

いずれかの段階で有効な候補が見つからなかった場合は、不完全な PE を出力せずエラーで復元を中断します。
